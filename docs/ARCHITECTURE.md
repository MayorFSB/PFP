# Архитектура: почему так

Разбор нетривиальных решений. Целевой масштаб — 100–1000 DAU на одном ноутбуке
(dev) и k3d-кластере (демо), поэтому нигде нет преждевременной оптимизации,
но каждая точка роста помечена.

## 1. Бронь без двойных записей

```
EXCLUDE USING gist (master_id WITH =, tstzrange(start_at, start_at + duration) WITH &&)
WHERE (status != 'cancelled')
```

- **Почему constraint, а не `SELECT FOR UPDATE` / сериализуемые транзакции:**
  конкурентность живёт в БД, а не в приложении. Два гонящихся запроса корректно
  разрешаются при любом числе воркеров и реплик приложения — условие гонки
  невозможно по построению, это доказуемо сильнее, чем «мы аккуратно залочили».
- **Idempotency-Key** (`bookings.idempotency_key UNIQUE`) — повторное отправление
  формы (двойной клик, ретрай сети) не создаёт вторую бронь: тот же ключ
  возвращает ту же запись. Ключ приходит с фронта, fallback — uuid на сервере.
- Кэш слотов в Valkey инвалидируется по событию бронирования/отмены, а не по TTL —
  между инвалидацией и TTL 120с окно, когда слот показывается свободным;
  финальная правда всё равно за constraint в БД.

## 2. Сессии: rotating refresh + reuse detection

- Access-JWT живёт 15 минут и в httpOnly cookie (не localStorage) — недоступен JS,
  уходит автоматически, SameSite=Lax режет CSRF-вектор.
- Refresh при каждом обновлении **ротируется**: старый токен помечается
  использованным. Повторное использование ранее сменноного refresh — признак
  кражи: сносят **все** сессии пользователя (`rotate()` в auth/service.py).
- Cookie для refresh — отдельный path-скоуп, у SSR-форм свой CSRF-токен
  (double-submit cookie + сравнение на сервере).

## 3. Пароли: Argon2id + pepper

- Argon2id (pwdlib) — memory-hard, устойчив к GPU-перебору; параметры в дефолтах
  библиотеки, верификация константным временем.
- Pepper из env (`PFP_PASSWORD_PEPPER`) добавляет секрет, которого нет в БД:
  слитый дамп без env-секрета не перебирается. Pepper ≠ соль: соль у каждого
  пароля своя и лежит в хэше, pepper один и живёт вне БД.

## 4. Кэш и формат данных

- Valkey: значение — JSON, gzip только при >1KB (мелкие ответы gzip только
  раздувает и тормозит). TTL 60–300с. Ключи версионированы префиксом `pfp:v1:` —
  сброс кэша деплоем = смена версии, без FLUSHDB.
- Персональные данные в кэш не попадают вообще (слоты — публичная сетка).

## 5. Наблюдаемость

- structlog JSON → Loki: логи запроса коррелируют по `rid` (request id).
- Prometheus: `bookings_total{filial}`, `http_latency` (p95), `cache_hit_ratio` —
  три метрики, на которые реально смотрят; Grafana-дашборд в репо
  (observability/grafana-dashboard.json).
- `/live` vs `/ready`: liveness — процесс жив (без зависимостей), readiness —
  реально пингует postgres (`SELECT 1`) и valkey (`PING`), при деградации — 503,
  чтобы оркестратор вынул под из балансировки.

## 6. Фронт: SSR без сборки

- Jinja2 + HTMX + один CSS-файл. Ни node_modules, ни webpack: точка отказа и
  поверхность обновлений = ноль, время до интерактива — размер HTML.
- CSP с nonce на каждый ответ (middleware `guard.py`), autoescape включён,
  CSRF на всех POST-формах.
- Исключение — 3D-hero на three.js (ES-модули, тоже без сборки). Параметры тюна
  в JSON (`static/3d/look-wash.json`) — правки визуала не требуют ни кода, ни
  деплоя статики.

## 7. Оплата: Strategy

`Provider` (протокол) + `FakeProvider`: checkout отдаёт URL, webhook подтверждает
по подписи. Идемпотентность webhook — по payment-id. Реальный провайдер = новый
класс, роутер и сервис не меняются.

## 8. Асинхронность

Весь стек async (FastAPI + SQLAlchemy 2.0 + asyncpg + redis.asyncio): один
процесс держит сотни соединений на медленных I/O (БД, Valkey, внешний chat-API)
без пула воркеров. Синхронных вызовов в async-путях нет (проверяется ревью).

## Точки роста (намеренно не сделаны)

| Когда понадобится | Что сделать |
|---|---|
| >5к DAU | read-replica для слотов/каталога, партиционирование bookings по дате |
| Мультирегион | вынести слоты в отдельный сервис, события через outbox |
| Оплата | реальный Provider + reconciliation по расписанию |
| Рост чата | очередь на генерацию ответов, rate-limit по пользователю |
